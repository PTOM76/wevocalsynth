# ドキュメントの書き方
`docs/` にドキュメントを足すときの決まり。新しく書くときは [templates/](templates/) のひな形をコピーして始める。

## どこに書くか

| 記述内容 | 場所 |
| --- | --- |
| プロジェクトの概要、すぐ動かす手順 | ルートの `README.md`（大まかに。詳しいことは docs へリンクする） |
| 1つのテーマの詳しい説明 | `docs/<テーマ>.md` |
| 実装中に問題を踏んで決まったこと | [DECISIONS.md](DECISIONS.md) |
| 関数・型の細かい説明 | コードのコメント。docs には概要と場所だけ書く |

1ファイル1テーマにする。既存のファイルに収まらないテーマなら新しく作る。読みたくない人の負担を減らすため、別の話題は別のファイルに分ける。

## ファイル名
特に指定するわけではないが、`docs/` 直下は英大文字にするのが好ましい（例: `ARCHITECTURE.md`、`SETUP.md`）。

## 読み手
リポジトリしか見られない、初めて WeVocalSynth に関わる開発者を想定する。
- 音声処理の用語（WSOLA、フォルマント、F0 など）は、初出で意味を書く

## 書き方（推奨）
- 3つ以上並ぶものや、項目ごとに説明が付くものは表にする
- 決まりごとには理由を書く。理由の無い決まりは守られないし、変えてよいかも判断できない
- 書き方の決まりは GOOD / BAD の例を並べる
- 関数名やファイルを挙げるときは、実在するものを使う。できる限り、削除されたら修正する

## リンク
- 相対パスで書く（`[決定事項](DECISIONS.md)`）
- 新しいファイルを作ったら、[docs/README.md](README.md) の目次に追加する

## 更新
- コードを変えて内容が食い違ったら、同じ変更の中でドキュメントも直す
- 処理時間や「未確認のこと」のような時点で変わる情報には日付を付ける（例: `(2026-09-27 時点)`）
