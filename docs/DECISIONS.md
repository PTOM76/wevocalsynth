# 決定事項
実装していて問題を踏み、その結果として決まったもの。知らずに触ると同じ問題を踏むので、新しいコードでも同じようにする。

設計全体の方針は [ARCHITECTURE.md](ARCHITECTURE.md)、書き方の決まりは [CODING.md](CODING.md) を参照。

## 音声処理

### 伸長の最後のフレームは、入力の最後のフレームに合わせる
最初は出力位置を伸縮率で割って入力位置を決めていた。これだと末尾でフレームが入力の終端をはみ出して無音を重ね合わせ、伸ばした音の最後だけギザギザになった。
はみ出さないよう位置を止めると、今度は最後の断片を何度も繰り返してうなりになった。

そのため `TimeMap::frame_pos` で「最後の出力フレーム＝最後の入力フレーム」になるよう対応づけている。すべての伸縮方式がこれを通る。テストは `stretch_tail_is_steady`。

### WSOLA の類似度はフレームの重なる部分だけで計算する
フレーム全体で比べると、末尾では比較する範囲が入力の外にはみ出す。重なる前半だけで比べれば常に入力の内側に収まり、計算量も半分になる。

### ピッチ変更は「伸縮してからリサンプル」で行う
長さはピッチ比に影響されず、ピッチ変更と時間伸縮を1回で指定できる。処理の順番で結果が変わる心配もない。

### 新しい処理方式を入れても、前の方式は残して選べるようにする
方式ごとに得意な音が違い、新しい方式がどの素材でも良いとは限らないため。既定はボーカル＝PSOLA、楽器＝Phase Vocoder で、処理モードの「…」から WSOLA・SOLA も選べる。

### 区切り位置は2乗誤差で探し、ゼロクロス点では区切らない
ゼロクロス点で区切る方式を試作して比べた。ボーカルもどきを4倍に伸ばしたときの周期のきれいさは、2乗誤差（SOLA）の 0.997 に対して 0.986〜0.995 で、低い声ほど悪かった。倍音が多いと位相が揃わないため。計算が軽い利点も、今の SOLA が十分速いので活きない (2026-09-30)。

### Phase Vocoder で2本をまとめて逆 FFT するときは、直流とナイキストのビンを実数にする
位相を回すと直流とナイキストのビンに虚部が付く。1本ずつ逆変換すれば虚部は出力の虚部に出て捨てられるが、2本を実部・虚部に詰めてまとめると相方に漏れた（直流の大きい音で大きくずれた）。
また、まとめるのは同じチャンネルの隣り合うフレームにする。違うチャンネル同士だと、大きな雑音側の計算誤差が相方の静かな帯域に漏れ、偽のピークができて結果が揺れた。

### フォルマント補正はリサンプルの前に行う
リサンプルの後だとピッチが上がって倍音の間隔が広がり、包絡をうまく推定できない。前なら元の声の高さのまま推定できる。

### ボーカル／楽器の自動判定は目安として扱う
「鳴っているフレームのうちピッチが取れた割合」で判定している。正弦波の和音は1つの長い周期を持つため、「ボーカル」と誤判定される（合成音で確認）。
初期値を決めるだけにし、画面の切り替えを優先する。実際の素材での精度はまだ確かめていない (2026-09-27 時点)。

### リアルタイムのループ試聴は、適用とは別の簡易な方式を使う
適用時の方式（PSOLA・WSOLA・Phase Vocoder など）は音声をまとめて処理する前提で、再生しながら少しずつ処理する形にするのは重い。
ループ試聴は AudioWorklet のグラニュラー方式にし、「適用」と通常の「試聴」は高品質な処理のままにした。音がザラつくのはこの割り切りのため。

## 実行と読み込み

### スペクトログラムと F0 は、表示を ON にしたときだけ計算する
ファイルを開いたときに表示の ON/OFF とパラメータを前のファイルから引き継いでいた。そのため開いた直後にスペクトログラム・F0・プレビューの処理が Worker に積まれ、読み込みが遅く感じられた。
今はファイルを開くと表示を OFF、パラメータを初期値に戻す。処理方式とフォルマント保持の ON/OFF だけは、好みの設定として残す。

### 再生位置を画面全体の状態にしない
再生位置を React の状態として 60回/秒 更新していたころは、再生中ずっと画面全体（MUI の部品が多い）が描き直され、1回に 50ms 以上かかって FPS が 20 まで落ちた。
再生中は状態を更新せず、再生位置の線・時間の表示・自動スクロールが `livePosition()` を自分で読む。これで FPS 60、長いタスク 0 になった。

### 重い処理はすべて1つの Worker に順番に送る
並列にすると WASM のメモリを複数持つことになり、長い音声では足りなくなる。順番に処理される前提なので、解析の結果は「どのクリップのものか」を確かめてから使う（古い結果を捨てる）。

### プレビューは、同じ設定のときだけ使い回す
「適用」で加工済みプレビューを差し込むときは、クリップ・範囲・パラメータがすべて同じかを確かめる。1つでも違うものを差し込むと、画面の設定と違う音になる。

### 追加機能のファイルは、ページを開く操作では保存先から返さない
`addons/` を保存先（Cache Storage）から返す設定が、ページを開く操作まで拾っていた。そのうえ、ページを開く操作はアプリ本体の `index.html` で返す設定（オフライン起動用）とも重なり、`addons/` のページを開くとアプリの画面になった。
そのため [vite.config.ts](../vite.config.ts) で、`addons/` はページを開く操作の対象から外し（`navigateFallbackDenylist`）、保存先から返すのはページを開く操作以外に限っている (2026-10-01)。

### 追加機能の進捗表示に Content-Length を使わない
GitHub Pages は `application/octet-stream` も gzip で配信し、`Content-Length` は圧縮後の大きさになる（乱数の 40MB で元より約 13KB 大きかった）。進捗はマニフェストに書いた元の大きさで計算する (2026-10-01)。

### Spleeter の fp16 版は WebGPU で動かさない
ONNX Runtime Web 1.30 の WebGPU で fp16 版を動かすと、エラーは出ずに出力がすべて 0 になった。入力は正しく渡っていた。int8 版・fp32 版は WebGPU でも正しく抽出できたので、fp16 版のときだけ WASM で動かす (2026-10-01)。

## 画面

### アイコンは Font Awesome を使う
`@mui/icons-material` は約3万ファイルあり、この環境ではインストールが時間切れで途中で止まり、一部のアイコンのファイルが欠けて壊れた。使うのは数十個なので Font Awesome に替えた。

### 見た目は角丸を抑え、配色は Google 製品寄りにする
Material 3 の既定（紫・大きな角丸・カプセル型のボタン）は、生成された画面らしい見た目になった。角丸は 4px、配色は青 `#1A73E8` にしている。
同じ理由で、説明文は短くし、背景色付きのボタンは使わない。

### ページ全体をスクロールさせない
パネルを縦に積んでページをスクロールさせていたころは、波形を見ながら「加工」を操作できず、使いにくさの大きな原因になっていた。
画面の高さにぴったり収め（`100dvh`）、スクロールはインスペクタ（スマホはタブのパネル）の中だけにする。Web ページではなく、デスクトップアプリ・モバイルアプリを作っているものとして画面を考える。

### 波形とピッチ帯を画面の主役にする
操作のほとんどは波形とピッチ帯の上で行うため、PC ではツールバーとステータスバー以外の高さをすべて編集領域に使い、設定はすべて右のインスペクタ（幅 320px）に寄せる。
波形の高さは固定値ではなく、置き場所の高さに合わせて伸び縮みさせる（`laneHeights`）。

### PC とスマホは別々に設計する
PC は Windows のアプリのような高さ32px のメニューバー、スマホは Android 風の上部バーと画面下の再生バー。同じ部品を縮めるだけだと、PC では広さを活かせず、スマホでは操作しづらい。

### メニューやダイアログの開閉アニメーションは短くする
既定の長さだと、ツールでは開くまでの待ちが重さとして感じられた。`theme.ts` で 70〜160ms にしている。

### メニューバーの文字は行の高さを固定して中央にそろえる
英字は Roboto、日本語はシステムのフォントで描かれ、フォントごとに上下の余白が違う。そのままだと「WeVocalSynth」と「ファイル」の縦位置がずれた。

### 選択範囲・波形・再生位置は色で描き分ける
波形は青、再生位置の線は文字色、拍の線はオレンジ、選択範囲はシアン（ライト `#0097A7` / ダーク `#4DD0E1`）。同じ青系や文字色にすると重なって見分けられなかった。選択範囲は波形などに隠れないよう最後に描く。

### スマホではページ全体を拡大縮小させない
アプリとして使うので、viewport と `touch-action` で止める。iOS Safari は viewport の指定を無視するため、`gesturestart` も打ち消す。波形のピンチは波形の横方向の拡大縮小に使う。

### 新しい版は、利用者が「更新」を押したときに切り替える
`autoUpdate` だと作業中に勝手に入れ替わる一方、iPad のホーム画面の PWA では開き直しても読み込み直さず、更新されないことがあった。通知して利用者が選ぶ形にし、画面に戻ったとき・1時間ごと・設定の「今すぐ確認」で新しい版を確認する。

### 文字は選択できないようにし、日本語は文節で折り返す
アプリの操作中にラベルの文字を選択してしまうため、入力欄・ファイル名・リンク以外は選択不可にした（`MuiCssBaseline`）。日本語は `word-break: auto-phrase` で文節ごとに折り返す（Chrome 系のみ効く）。

### Canvas はライト/ダークに応じた色を自分で取り出す
`theme.palette` は常にライトテーマの値だった。そのまま Canvas に使うと、ダークテーマで波形の目盛りの文字が暗いまま見えなくなった。`usePalette()` を使う。

### スライダーの目盛りの色は明示する
MUI の既定では、目盛りがバーの上では背景色、外では文字の補助色で描かれ、どちらも背景と混ざって見えにくかった。`theme.ts` で色を指定している。

## データ

### 元に戻す履歴は差分だけを持つ
以前は1段ごとに音声まるごとのコピーを持っていて、3分のステレオで20段だと約1.3GB になり、タブのメモリ（ヒープ）が 1.9GB に達した。
今は前後のクリップで変わった部分だけを持つ（先頭・末尾の一致する部分を除く）。段数（既定50）とメモリ（既定512MB）の上限は設定で変えられる。

### プロジェクトファイルに元に戻す履歴は含めない
含めるとファイルが大きくなりすぎる。音声は gzip しても縮みにくく（10秒＋12秒のステレオで約7.6MB）、圧縮に数秒かかって画面が固まったため、.wvsp は無圧縮にした（保存 4.6秒 → 0.05秒）。古い gzip のファイルも読める。

### 自動保存は IndexedDB に置く
音声は localStorage の容量（約5MB）に収まらない。設定のような小さいものは localStorage に置く。

### 自動保存の書き込みは Worker で、ブラウザが空いているときに行う
メインスレッドで保存すると、長い音声で画面が固まった。Worker に渡してから書き込み、原音は変わったときだけ保存する。

### 起動時の復元が終わるまで自動保存しない
復元の前に保存が走ると、まだ何も開いていない状態で前回の作業を上書きしてしまう。

### 多言語化の JSON はビルド時に取り込む
実行時に読み込むと、表示までに待ちが出る。Vite がバンドルに取り込むので待ちはない。ファイル名は Minecraft と同じ `ja_jp` / `en_us`。
